# Agent instructions

Read `README.md`, `docs/operations.md`, and `SECURITY.md` before changing or
deploying this project. These instructions apply to the whole repository.

## Scope and architecture

- This is a public, reusable template. Deployment-specific state stays private.
- Operate only on the host and Compose project selected by the user. Local code
  or documentation work does not authorize changes to a running VPS.
- Xray accepts VLESS + REALITY and forwards TCP through authenticated GOST in
  the WARP container. Keep WARP off public host ports and the optional probe on
  host loopback. Preserve separate network namespaces and the TCP-only contract.
- Preserve the absence of a direct client-egress outbound. Do not add fallback,
  change the tunnel implementation, or enable UDP as an incidental fix.
- `versions.env` owns image pins; `.env` owns deployment settings;
  `secrets/identity.json` owns credentials. `runtime/` is generated by `manage.py`.
  Change the renderer instead of editing generated files as a lasting fix.

## Privacy

- Never commit or print credentials, client URIs, registration state, live
  configuration, private endpoints, machine paths, or raw operational logs.
- Keep `.env`, `secrets/`, `runtime/`, `data/`, and backups ignored. Use only
  documentation addresses and domains in public examples and synthetic fixtures
  in tests. Preserve restrictive directory and file permissions.
- Give users private client-file locations and retrieval instructions by default.
  Do not paste their contents into public issues, commit messages, or CI output.
- Before every commit, inspect `git diff --cached` and the staged file list, then
  run `python3 scripts/check-public.py`. Review author metadata and remote URLs.
  The scanner is heuristic; it cannot decide whether an endpoint is private.

## Deployment and recovery

1. Inspect the selected host's architecture, resources, existing containers,
   listeners, routes, firewall, and Docker networks. Select unused ports and a
   subnet that does not overlap existing routes. Preserve SSH and other services.
2. Verify the REALITY target from that host. Check the installed WARP client and
   its actual mode and tunnel protocol; do not infer them from an image tag.
3. For an existing installation, preserve its identity and WARP registration.
   Back up the current source revision, image pins, settings, and private state
   before an update, following `docs/operations.md`. Use `init` only for a new node.
4. Use `./compose.sh` so both environment files are loaded. Render and validate
   configs, pull the selected images, then update explicit services only. Start
   WARP and wait for health before Xray. Recreate affected containers after
   rendering because atomic file replacement does not refresh a live bind mount.
5. Verify backend authentication/DNS/egress, the REALITY probe, and an external
   client through the public listener. Require `warp=on` or `warp=plus` and a
   second HTTPS destination. Check pre-existing services after the operation.

Do not use broad restarts, `compose down`, prune, destructive synchronization,
or changes to shared networks/firewalls outside the requested scope. Do not
delete registration state, rotate credentials, or repeatedly restart containers
to try to obtain a different exit IP. Diagnose before changing persistent state.

## Validation and evidence

- For code changes, run `make test`; add tests for meaningful behavior changes.
- For generated configuration or Compose changes, also run `manage.py check`
  against an isolated fixture installation using the pinned images.
- For documentation-only changes, review the diff and run the staged privacy
  check. Do not use production hosts to validate documentation or repository layout.
- A healthy container or valid config does not prove an external client works.
  Report skipped and failed checks explicitly, with credentials redacted.
- Distinguish connection reliability, protocol blocking, and destination IP
  reputation. Do not promise a fixed exit IP, uninterrupted service, or immunity
  from detection. Compare alternatives using measurements on the intended path,
  including long connections and recovery, before recommending a migration.
